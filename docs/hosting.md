## Personal-first storage direction

The user clarified on **2026-10-12** that the current product is personal productivity: one developer's view and planning over GitHub's repository network. A separate PostgreSQL service is optional, not a prerequisite for this vision. Keep provider details behind the storage interface and choose the smallest durable implementation that supports the workflow.

- **Cloudflare Durable Objects:** recommended for the current deployment. The existing SQLite adapter already provides transactional state changes and history, without an external database. Cloudflare documents [SQLite transactions](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactionsync) and [durable alarms](https://developers.cloudflare.com/durable-objects/api/alarms/); the current implementation wakes jobs through Worker cron.
- **Private Vercel Blob:** a plausible alternative for small personal JSON state. Its API supports [ETag conditional writes](https://vercel.com/docs/vercel-blob#conditional-writes) and [fresh private reads with `useCache: false`](https://vercel.com/docs/vercel-blob/private-storage#consistent-reads). There is no Blob adapter today. A proposed adapter could replace one bounded scope document containing state and its audit history together; separate blob writes would not satisfy the current atomic state/history contract. Durable claims, pending actions, conflict retries and scheduler wakeups would still need application logic and verification.
- **External PostgreSQL:** retain the implemented option when one database across hosts or richer querying is useful. Portability does not require using it in the current Cloudflare deployment.

Personal preferences naturally use a stable numeric GitHub user ID. Current plans and automation are keyed by installation/repository; plan ownership is a follow-up product boundary, not changed by this hosting recommendation. Even one user has concurrent browser tabs, webhook deliveries and background jobs. Real PR automation needs a common record of its actions so those paths do not independently release or roll back the same review.

## Current durable state contract

`src/server/state/types.ts` defines provider-neutral typed read/list/compare-and-swap operations. Keys use the stable numeric installation and repository IDs; records cover plans, workflow configuration, generations/claims/outbox, delivery inbox and jobs. Authentication, current repository/actor permissions, CSRF and management grants remain above this boundary. No authoritative coordination state lives in process memory, browser storage or a server filesystem.

External PostgreSQL is the common durable option for both providers. Set `DATABASE_URL` and `STATE_STORE=postgres`; the implemented transport uses Neon's HTTP-compatible PostgreSQL driver. The SQL adapter itself accepts an injected query transport for another compatible PostgreSQL client. [Neon's driver documentation](https://github.com/neondatabase/serverless) describes its Node/worker support. The application does not create a database account or invent credentials.

Apply [the schema migration](../migrations/001_shared_state.sql) deliberately using `pnpm migrate:state` with `DATABASE_URL` in the operator environment. Each expected-version decision, value change and audit append is a single PostgreSQL statement/transaction. Stale writes make no value or audit change. Reads of records plus history share one snapshot. The same durable record/CAS contract fences worker claims and inbox replay across restarts.

Cloudflare's existing SQLite Durable Object remains an optional adapter (`STATE_STORE=durable-object`), with its current binding and migration retained. Existing planned-assignment rows are preserved. New workflow/resources and audit tables are added in the object's constructor. Choosing this adapter ties storage to Cloudflare; choose the common PostgreSQL store to switch hosts without moving coordination data. Cross-provider cutover must use the same database and `AUTH_SECRET` deliberately, preserve callback configuration, and keep management scope unchanged; switching hosts must not enroll stacks.

## Workflow operator configuration

Workflow writes remain off unless deliberately enabled and an actual stack is enrolled. Store these values through the chosen provider's secret configuration:

- Existing sign-in credentials: `APP_ORIGIN`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `AUTH_SECRET`; optional actual `GITHUB_APP_SLUG`.
- Shared state: `DATABASE_URL` and `STATE_STORE=postgres`, or the optional Cloudflare Durable Object binding.
- Background principal: actual `GITHUB_APP_ID` (or supported client issuer), `GITHUB_APP_PRIVATE_KEY`, and `GITHUB_WEBHOOK_SECRET` of at least 32 characters.
- Runner: `WORKFLOW_RECONCILE_SECRET` of at least 32 characters; optional Vercel `CRON_SECRET` for its GET wakeup.
- Explicit selected scopes: `WORKFLOW_REPOSITORIES`, a JSON array containing actual numeric `id`, `installationId` and `full_name` values. Empty `[]` starts no repository work. Never copy fixture IDs into production.
- Deliberate write enablement: `GITHUB_WORKFLOW_WRITES_ENABLED=true`, only after the existing App's required Pull requests write permission, installed scope and real behavior are reviewed.

Webhooks are HMAC-verified over a bounded raw body and persisted before acknowledgment. Cloudflare intercepts exact `POST /api/github/webhook` in its native entry before framework request setup, using explicit trusted environment/store selection. Node/Vercel use the same receipt core through the API route. Both enforce signature/scope, durable receipt and deduplication; neither dispatches GitHub actions inline. A separate authenticated scheduler reloads current GitHub state and grants. Leases, generations, uncertain outcomes and retries live in durable state; browser sessions are not the scheduler.

The selected live pilot has all background credentials, accepted PR-write access and active signed subscriptions. Its real effects and native cron progression passed. Intermittent empty HTTP 500 deliveries persisted after ingress hardening, while safe replay and subsequent deliveries returned 202. This remains an unresolved runtime/delivery issue; writes and feature automation are paused. See [pilot evidence](pilot.md).

Run `pnpm workflow:reconcile` once from any authenticated scheduler, or use `--watch` beside a long-running Node process. The source Dockerfile starts the generated Node server and configured runner; no credentials enter its build context. Cloudflare has a native minute trigger. On Vercel, select an external wakeup runner or review the Pro cron requirement; a paid Vercel plan is not forced by this repository. Credentials, App permission changes, webhook subscription, database provisioning, actual scope IDs and hosted publication remain operator/account steps.

## Verification commands

`pnpm test:storage` exercises actual workerd/SQLite restart, plan preservation, concurrent claims and inbox replay. `pnpm test:postgres` requires an explicitly supplied isolated localhost `TEST_DATABASE_URL` for the dedicated `mergefoo_test` fixture; it never reads production `DATABASE_URL`. It verifies transactional CAS/audit, competing claims, scope isolation, shared plans, inbox replay and restart persistence.

After a credential-free Vercel build, `pnpm test:host:vercel` runs its emitted handler without outbound network. Node output is exercised through its generated server entry. Unit/browser fixtures and local database/runtime checks remain distinct from real GitHub account and hosted verification.

### Request budget boundary

The adapter batches review/timeline and classic-policy evidence, reads overflow only when needed, briefly caches verified no-approval-policy evidence and proves effects with target-only queries. It bounds GitHub requests and leaves work queued when verification cannot complete.
